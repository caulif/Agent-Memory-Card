# Risk Assessment And Production Gap Analysis

> Generated by spec-driven-develop Phase 1 on 2026-05-18.

## Phase 2 Deep-Discuss Framing

### Problem Validity

The user's concern is valid: "I do not want to use my own tool yet" is not merely a mood signal. It indicates that the value loop is not earning trust fast enough.

The codebase has serious work behind it, but production usefulness depends less on how many concepts exist and more on whether one real daily workflow is obvious, reliable, explainable, and reversible.

### Information Sufficiency

The repository contains enough information to make a grounded improvement plan:

- README and feature docs define the product thesis.
- Iteration backlog and completion audit reveal known weak spots.
- Rust/React/Tauri code shows the implemented architecture.
- Tests and golden-set fixtures show the quality strategy.
- GitHub pre-flight confirms `GITHUB_FULL` can be used once a confirmed plan should be synchronized.

The only missing information is direct user telemetry from real sessions: where the user hesitates, which candidates they reject, and how often a synced Memory Card improves future agent behavior.

## Top Product Risks

### 1. The daily loop is still too concept-heavy

The UI exposes several valid internal concepts: Candidate, Draft, Memory Card, Assignment, Artifact, Drift, Job, Catalog, Quality, Provider, and Kernel Policy.

For a production tool, the default path should feel like:

```text
Review suggestions -> trust evidence -> approve -> see diff -> sync -> verify
```

If the user has to learn the internal data model before getting value, the product will feel like a developer console.

Risk severity: P0

### 2. Evidence exists but is not yet the center of trust

The project stores evidence, confidence, extraction metadata, and pipeline reports. But the user should not need to hunt for evidence. Every candidate should answer:

- What sentence or conversation proved this?
- Did this happen once or recur?
- Is it a durable preference, a one-off request, or a risky instruction?
- What exact card and artifact change will result?

Risk severity: P0

### 3. Quality gates are promising but not yet productized

Golden Set regression and eval reports exist. The latest audit reports strong deterministic scores, but also notes that real provider evidence validity still needs capture and more rejected examples.

If evaluation remains a developer-only CLI activity, extraction quality will still feel subjective to the end user.

Risk severity: P0/P1

### 4. Artifact sync is strategically strong but needs recovery polish

Drift detection, import/keep/discard, and diff preview are real strengths. They are exactly the kind of production trust boundary this product needs.

Remaining risk:

- large drift sets need per-file recovery operations and clearer progress
- destructive discard flows must stay very explicit
- sync should always leave a visible audit trail and rollback/checkpoint hint

Risk severity: P1

### 5. Extraction complexity may outpace measurability

The five-layer pipeline is directionally good:

```text
STRIP -> TRUNCATE -> CLUSTER -> INDUCE -> CRYSTALLIZE
```

The risk is that pipeline changes become hard to reason about because large modules, prompts, thresholds, evidence selection, and provider behavior all interact.

Mitigation: every pipeline change must report recall, precision, one-off false positives, duplicate risk, evidence validity, latency, and provider failure rate.

Risk severity: P1

### 6. Large modules reduce agent collaboration quality

Several files exceed 800-1600 lines. This increases the chance that future AI-assisted edits miss context or cause unrelated changes.

Risk severity: P1

### 7. Onboarding and release are not yet boring

The README says normal Windows users should prefer releases, while the current workflow still emphasizes dev commands. Production adoption requires a boring first-run path:

- install
- open
- add project
- run first analysis
- review first suggestion
- sync safely

Risk severity: P1/P2

## S.U.P.E.R Architecture Health Summary

### S - Single Purpose

Current health: Partial to weak.

Violation hotspots:

- `src/extract/*` mixes research pipeline, provider integration, quality, report logic, and test evolution history.
- `src-tauri/src/commands/core.rs` routes too many command families.
- `app/src/main.tsx` wires too much app-level behavior.
- CSS files are too broad.

Priority response: split along product workflow boundaries, not arbitrary technical layers.

### U - Unidirectional Flow

Current health: Partial.

The intended flow is source -> suggestion -> card -> assignment -> artifact. However, UI and service layers still need clearer read-model and command boundaries.

Priority response: define canonical read models for Review Inbox, Memory Library, Agent Loadout, Artifact Preview, Jobs, and Evals.

### P - Ports over Implementation

Current health: Partial.

The file-native store is a strong port. But provider APIs, extraction outputs, candidate/draft transitions, and frontend read models need tighter schemas and versioning.

Priority response: formalize Suggestion, Evidence, ArtifactDiff, EvalRun, and JobResult schemas.

### E - Environment-Agnostic

Current health: Stronger than other principles.

The project is local-first, file-native, and avoids mandatory DB infrastructure. Windows is the current release target, which is acceptable if explicitly documented.

Priority response: make provider/proxy/config diagnostics visible so setup failures become actionable.

### R - Replaceable Parts

Current health: Partial.

Good replaceability exists around artifact targets and kernel policy. Weak replaceability exists around extraction providers, UI feature slices, and large command surfaces.

Priority response: make each production loop segment replaceable independently.

## Production Improvement Thesis

The next major effort should not be "add more features". It should be "turn the existing pieces into one trusted daily workflow".

Recommended north star:

```text
In under 10 minutes, a first-time user can install the app, select one real project, extract 3-8 high-signal suggestions, inspect evidence, approve one Memory Card, preview the exact AGENTS.md/CLAUDE.md diff, sync it, and know how to undo or refine it.
```

## GitHub Tracking Risk

`GITHUB_FULL` is available. However, creating Issues and a Project board before the user confirms scope would turn exploratory analysis into task clutter.

Recommendation: use GitHub only after the user confirms the proposed roadmap. Then create:

- one Project board: `Spec: Agent Memory Kernel Production Tooling`
- milestones for workflow hardening, evidence/eval, sync/recovery, release/onboarding, and architecture cleanup
- one issue per confirmed task with acceptance criteria and S.U.P.E.R drivers

## Key Decision Needed From User

The next plan should prioritize one of two product bets:

1. **Production daily workflow first**: make the core review-sync loop something the owner actually wants to use every day.
2. **Extraction quality first**: make the algorithm and eval system much more reliable before further UI polishing.

My recommendation is option 1, with evaluation embedded as a quality gate, because the current pain is "I don't want to use it", not "the clustering algorithm is academically incomplete".
