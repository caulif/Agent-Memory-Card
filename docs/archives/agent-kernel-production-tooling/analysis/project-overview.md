# Agent Memory Kernel Project Overview

> Generated by spec-driven-develop Phase 1 on 2026-05-18. Focus: understand why the project still does not feel like a practical production tool and identify improvement directions.

## Product Intent

Agent Memory Kernel is a local-first Memory Card workbench for Claude Code and Codex users. Its intended workflow is:

```text
Local conversations / project rules / skills
  -> Observation
  -> Candidate / Draft
  -> reviewed Memory Card
  -> assignment to agent targets
  -> generated native artifacts such as AGENTS.md, CLAUDE.md, and skills
```

The strongest product thesis is not "automatic memory". It is "auditable memory governance": the tool should help a user extract durable agent knowledge from real work, review it, assign it, preview file changes, and safely sync it back to each agent's native instruction surface.

## Current Production Strengths

- The core product boundary is unusually mature for a pre-1.0 tool: generated artifacts are treated as build products, not the source of truth.
- Human review is built into the model. Drafts and candidates are not silently promoted into long-term memory.
- There is real drift protection for generated artifacts, including import/keep/discard flows.
- The project already has a quality-gate direction: golden-set regression, eval reports, evidence validity, and deterministic test fixtures.
- Long-running work is moving toward Jobs, which is essential for a desktop production tool.
- Tauri mutating commands route through `KernelPolicy` and decision tokens for higher-risk operations.
- The codebase has meaningful tests across Rust core, Tauri service, frontend utilities, and extraction quality.

## Current Product Shape

The project is not an empty prototype. It has many of the right components. The core problem is that these components do not yet collapse into one obvious daily loop.

The intended loop is:

```text
Open app
  -> choose project
  -> run evolution
  -> inspect a few high-quality suggestions
  -> approve/edit/reject
  -> assign to Codex/Claude Code
  -> preview exact artifact diff
  -> sync
  -> verify the agent will now behave differently
```

The current experience risks feeling heavier than the value it delivers because it exposes many internal concepts at once: Candidate, Draft, Memory Card, Assignment, Quality, Catalog, Job, Drift, Provider, Kernel Policy, and Evaluation.

## External Ecosystem Context

The ecosystem is moving toward file-based instructions, agent skills, MCP tools, and explicit long-term memory operations.

- Codex uses `AGENTS.md` as a project instruction surface, which makes this project's compiler target strategically sound.
- Claude Code has skills and project instruction surfaces, also making a native exporter valuable.
- MCP has normalized tool/server integration as a portable agent capability layer.
- Memory systems such as Mem0 treat add/search/list/update/delete as explicit lifecycle operations, which supports this project's governance-first direction.

The product should therefore avoid being "yet another memory store". Its defensible angle is a local, inspectable compiler and governance layer for agent memory.

## Primary Diagnosis

The project is close in architecture but still far in product feel.

The missing production quality is mostly not another extraction algorithm. It is the feeling that the user can trust the tool in five minutes:

- What exactly did it discover?
- Why is this candidate true and durable?
- What evidence supports it?
- Where will it be written?
- What changed compared with the current generated files?
- Can I undo or recover safely?
- Did this actually improve future agent behavior?

Until these questions are answered directly in the default path, the tool will feel more like a research workbench than a production tool.
